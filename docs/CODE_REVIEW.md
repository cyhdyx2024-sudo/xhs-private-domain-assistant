# 代码与安全审查记录（更新于 2026-08-31）

本文档公开记录一次针对本项目的完整"红队攻击 + 场景实测 + 代码审查"，保持工程透明。

## 一、红队攻击（服务端，25 项）

对产品模式实例执行：鉴权绕过、跨租户越权（IDOR）、SQL 注入、存储型 XSS、路径穿越、
SSRF（含 userinfo@ 绕过、伪造后缀域名、内网地址）、CSV 公式注入、超大请求体、注册洪水。

**结果：鉴权、租户隔离、SQL 参数化、模型域名白名单（含 @ 绕过）、内网防护全部守住。**
发现并已修复：

| # | 问题 | 修复 |
|---|------|------|
| 1 | 超大请求体触发未捕获异常，连接被硬切且日志刷 Traceback | 返回 413 JSON |
| 2 | `/tenant/register` 应用层无限流（无 nginx 的自托管用户会被灌爆租户表） | 每 IP 每分钟 10 次（X-Forwarded-For 感知） |
| 3 | 线索 CSV 导出存在 Excel 公式注入面 | 前缀 `=+-@` 的字段加 `'` 转义 |
| 4 | 客户线索无删除接口（数据擦除权） | 新增 `POST /leads/delete`、`/leads/clear` |
| 5 | 默认非产品模式 + `CORS: *` + 服务端凭据回退 = 任意网页可把本机 Bridge 当免费 LLM 代理 | 产品模式改为默认开启；CORS 仅回显可信来源（XHS 域 / 扩展 / 本机）；`/reply` 对不可信来源直接 403 |

## 二、场景质量实测（10 个真实对话）

价格追问、愤怒客户、英文客户、多轮上下文引用、留资确认、提示词注入、诱导虚假承诺等 10 个场景。

**第一轮发现 P0**：客户问"你加我微信了吗"，AI 编造"已经搜索 abc123 提交好友申请了"——
守卫正则只防将来时承诺（"马上加"），漏了过去时虚构（"已经加了"），且状态检测门漏掉
"加我微信了吗"这类带代词间隔的问法。**已修复并加入回归测试。**
修复后 10/10 场景通过，无虚假承诺、无提示词泄漏、无重复索要联系方式。

## 三、静态审查（扩展 + 服务端，30 项）

完整审查 `content.js` / `safety.js` / `options.js` / `agent.py`。V1.0 审查时技术债评分为 **6/10**；
V1.1.0 收敛到约 **4/10**：不是垃圾堆，安全规则、文本渲染、请求中止、消息签名和服务端模块边界都已建立，
但 `content.js` 仍偏大，DOM 适配与调度状态尚未真正分层。

已修复：

- `rewrite_fallback` 动作、"fallback_text"、"temperature" 之前被服务端完全忽略（双倍 LLM 成本的盲重试）→ 已实现
- 合法的短回复（<24 字）被 503 拒绝 → 阈值调整为 6，避免误杀
- 多标签页重复发送 → 后台租约仲裁 + storage 状态同步
- 401 后静默创建新工作区 → 保留原身份、停机并提供本机令牌重签命令
- 正文中的时间字样污染消息年龄 → 只读取专用时间节点
- 跨客户残留草稿 → 切会话前快照并清空，返回原会话时按签名恢复
- 不确定发送绕过小时上限 → 已点击但未回读的发送也按一次额度计账

## 四、2026-08-31 真实页面回归新增发现

在真实小红书专业号私信页只读回归，没有发送客户消息。发现并修复：

| 严重度 | 发现 | 修复 |
|--------|------|------|
| P1 | 消息区使用父容器 180° 翻转，`scrollTop=0` 才是最新消息；普通列表算法会滚向旧消息 | 运行时识别变换矩阵，分别处理正向/倒置滚动 |
| P1 | 顶部店铺名 `.user-nickname` 被当成右侧客户名，令当前会话永久处于“不稳定” | 右侧姓名校验排除顶部账号栏，无可靠右侧姓名时以高亮会话 `data-key` 为准 |
| P1 | 本机仍运行 8 月 29 日启动的开发模式 Bridge，界面却静态显示“本地就绪” | 重启到当前安全默认；设置页增加真实健康检查和产品模式告警 |

**仍未完成（诚实列表）**：

| 严重度 | 问题 | 下一步 |
|--------|------|------|
| P1 | 最新两项 DOM 修复还需要重新加载扩展并刷新页面后做二次实机确认 | 保持全自动关闭，验证身份、滚动、预填和切会话 |
| P1 | 全自动真实发送链路没有在客户账号上执行破坏性回归 | 只在专用测试账号/测试会话验证，不能拿真实客户试错 |
| P2 | 平台 DOM 选择器仍可能随小红书改版失效 | 抽离 `xhs-dom.js`，保存匿名化 DOM fixture 做适配测试 |
| P2 | 退避、草稿等运行时 Map 主要依赖页面生命周期释放，长时间不刷新时缺少统一容量上限 | 调度层统一 TTL 与容量裁剪 |
| P2 | 平台极端情况下若缺少 `data-key`，同名昵称仍会使用同一回退键 | 缺少稳定 UID 时禁止全自动，不以昵称作为发送身份 |

## 五、重构路线（按收益排序）

1. **`xhs-dom.js`**：优先把联系人、消息、输入框、发送按钮与滚动方向识别收口到可测试接口；这次两个 P1 都来自 DOM 假设。
2. **`scheduler.js`**：把定时器、活动检测、退避、熔断和小时账本收口，统一 TTL 与容量上限。
3. **`store.js`**：以 schema 管理持久状态和迁移；跨 Tab 租约已经先行修复，无需为了形式立刻大拆。

结论：现在不做大爆炸重构——量级未到；先按上面的顺序拆，每拆一层补一层测试。
